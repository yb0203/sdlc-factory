# 🔤 Projection Units Nomenclature Options (`PROJECTION_UNITS_NOMENCLATURE_COMPARISON.md`)

## Executive Summary
This document compares four candidate naming paradigms for our **4 Provably MECE Projection Units** (`P_1, P_2, P_3, P_4`) to determine the single most elegant, evocative, and mathematically precise nomenclature.

---

## 🔬 Deep Dive into the 4 Options

### Option A: Physics & Mechanics Paradigm (`Action`, `Constraint`, `Relation`, `Attestation`)
- **`Action`** (State mutation & execution work: codegen, DB migration, test runner).
- **`Constraint`** (Declarative boundary: DoR/DoD policies, API schemas, SLAs).
- **`Relation`** (MECE graph relationship edge: Space, Time, Contract, Lifecycle).
- **`Attestation`** (Verifiable certificate: Z3 SMT solver proof + DSSE seal).
- *Best For*: Systems engineering & formal enterprise architecture.

### Option B: Compiler Theory & Phoenix Paradigm (`Delta`, `Contract`, `Edge`, `Proof`)
- **`Delta`** (Direct alignment with Phoenix Architecture: $\text{Desired} = \text{Current} + \text{Delta}$).
- **`Contract`** (Direct alignment with Design-by-Contract & Spec-Driven Development).
- **`Edge`** (Direct alignment with Graph Compiler Theory).
- **`Proof`** (Direct alignment with Formal Verification & Z3 Theorem Proving).
- *Best For*: Mathematically rigorous compiler-driven SDLC factories.

### Option C: Concise Monosyllabic Paradigm (`Exec`, `Rule`, `Edge`, `Seal`)
- **`Exec`** (Execution Unit)
- **`Rule`** (Declarative System Boundary)
- **`Edge`** (Graph Connection)
- **`Seal`** (Cryptographic / SMT Seal)
- *Best For*: Code cleanliness & developer brevity.

### Option D: Epistemic & Invariant Paradigm (`Work`, `Invariant`, `Relation`, `Certificate`)
- **`Work`** (Execution output)
- **`Invariant`** (Preserved system condition)
- **`Relation`** (Graph dependency)
- **`Certificate`** (Cryptographic / Mathematical proof certificate)
- *Best For*: High-assurance critical systems.
